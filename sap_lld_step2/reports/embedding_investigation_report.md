# Embedding quality investigation — report

Investigation into whether the step-2 embedding model's semantic-similarity signal is
trustworthy enough to weight heavily in step 3's scoring, following up on a 3-chunk
qualitative check during `ZORDER_MGMT_extract.txt` validation that suggested it might not
be. Ground truth for "related" vs "unrelated" comes entirely from the graph tables already
in the database (`object_calls`, `object_uses_table`) — no hand-picked pairs.

Data: the 15 objects / 59 chunks already loaded from `ZORDER_MGMT_extract.txt`. Nothing in
step 2 (extraction, parsing, chunking, or the original model's stored embeddings) was
modified for this investigation.

## Ground-truth pair set

All `C(15,2) = 105` object pairs were labeled mechanically:

- **43 related**: 23 pairs via a direct call edge (either direction), 28 pairs sharing at
  least one table, with 8 pairs qualifying both ways.
- **62 unrelated**: no call edge in either direction, no shared table.

Each object pair was expanded into every cross-combination of its objects' chunks, giving
**855 related chunk-pairs and 750 unrelated chunk-pairs** (1,605 total) from the raw chunk
set, or 601/506 (1,107 total) after excluding chunks under 15 characters (see artifact
below). Both exceed the ≥20/≥20 target comfortably — see the sample-size caveat at the end
for what this larger-than-expected count does and doesn't buy us.

**Correction to the original 3-chunk check**: that check treated
`ZCL_TAX_CALCULATOR.calculate_tax` as an "unrelated" comparison to
`ZCL_PRICING_ENGINE.calculate_order_total`. The graph's own ground truth says otherwise —
`ZCL_PRICING_ENGINE` directly calls `ZCL_TAX_CALCULATOR` (`object_calls` row id 292). That
pair was actually **related**, mislabeled by hand-picking. This is exactly the failure mode
the brief anticipated by requiring mechanical labeling instead of judgment calls, and it's
now corrected in this benchmark.

## A chunking artifact found along the way

All 10 `CLASS` objects produce an identical trailing chunk: the single line `"ENDCLASS."`,
left over after the chunker's last `METHOD`/`ENDMETHOD` boundary. Being character-identical
text, these 45 pairs (`C(10,2)`) embed to exactly zero cosine distance under both models,
regardless of whether the two classes are actually related — polluting both groups' low end
equally. The benchmark script supports `--min-chunk-length` to exclude these from the
analysis; both raw and filtered results are reported below since filtering barely changes
the overlap conclusion. **Not fixed here** — chunking parameters are out of scope for this
task — but worth flagging for step 2 chunking as a low-effort improvement (e.g. merging a
trailing chunk under some minimum length into its predecessor).

## Results — both models, with and without the trivial-chunk filter

| Embedding source | Filter | n (rel/unrel) | mean dist (rel / unrel) | median (rel / unrel) | mean gap | Cohen's d | overlap % |
|---|---|---|---|---|---|---|---|
| `all-MiniLM-L6-v2` (original) | none | 855 / 750 | 0.6621 / 0.6831 | 0.6633 / 0.6888 | +0.0209 | **0.096** | 45.9% |
| `all-MiniLM-L6-v2` (original) | ≥15 chars | 601 / 506 | 0.5934 / 0.6102 | 0.6026 / 0.6096 | +0.0168 | **0.124** | 47.2% |
| `st-codesearch-distilroberta-base` (code-aware) | none | 855 / 750 | 0.6921 / 0.7057 | 0.7139 / 0.7305 | +0.0136 | **0.069** | 46.3% |
| `st-codesearch-distilroberta-base` (code-aware) | ≥15 chars | 601 / 506 | 0.6548 / 0.6643 | 0.6694 / 0.6720 | +0.0095 | **0.067** | 49.0% |

"Overlap %" = fraction of unrelated pairs scoring at least as close (≤) as the median
related pair — the direct generalization of the original 3-pair problem (where the
"unrelated" pair scored closer than the "related" one). Cohen's d values around 0.1 or
below are conventionally considered negligible (small starts around 0.2).

Full 10-bin distance-distribution histograms for all four runs were generated by
`embedding_bench.py` and are reproduced in the appendix below — visually, the related and
unrelated distributions sit almost on top of each other for both models across the entire
range.

**Model chosen for the code-aware comparison**: `flax-sentence-embeddings/st-codesearch-distilroberta-base`
— open-source, a proper `sentence-transformers` checkpoint (no custom pooling code needed),
~300MB, downloads once then runs fully offline on CPU, trained specifically for code
search/similarity (though on code-search-net languages, not ABAP specifically — see
caveats).

## Comparison and recommendation

**Which model separates better?** Neither, meaningfully. The general-purpose model
(`all-MiniLM-L6-v2`) actually shows a *slightly larger* (still negligible) effect size
(d ≈ 0.10–0.12) than the code-aware model (d ≈ 0.07) on this sample — the opposite of what
you'd hope switching to a code-specific model would buy you. Given the small sample and the
tiny absolute gap between the two models' effect sizes, this should not be read as "the
general-purpose model is better for ABAP" — it should be read as "neither model produces a
separation signal large enough for the difference between them to mean anything yet."

**Is either model's separation strong enough to trust standalone?** No. In every
configuration, roughly **46–49% of unrelated pairs score at least as similar as the median
related pair** — essentially a coin flip. An embedding-only similarity ranking over this
package would be barely better than random at distinguishing a functionally-connected chunk
from an unconnected one.

**Recommendation for step 3's weighting.** The brief's default of 0.65 semantic / 0.35
structural should be inverted for this domain, at least until better evidence exists:
something like **0.25–0.35 semantic / 0.65–0.75 structural**, with structural signal
(the graph: direct calls, table sharing, hop distance) doing the primary ranking work and
embedding similarity used as a secondary tiebreaker within a structurally-plausible
candidate set, not as the primary filter. The graph-derived ground truth *itself* is doing
better in this investigation than either embedding model's distance — using it as the main
signal in step 3 has a stronger evidentiary basis right now than semantic similarity does.

**Is switching embedding models worth it?** Not on this evidence. The code-aware model adds
a second local model to maintain (a ~300MB download, another CPU inference path) for a
change in separation quality that is not just small but in the wrong direction on this
sample. Recommend keeping `all-MiniLM-L6-v2` as the default for now and revisiting the model
choice once a larger, real extraction file is available — see caveats below for why this
sample can't settle the question either way.

## Caveats on sample size and generalization

- **15 objects is small.** 105 object pairs and ~1,600 chunk pairs sound like a lot, but
  they're generated from only 15 underlying objects — the true degrees of freedom are much
  lower than the pair count suggests, since each object's chunks appear in many pairs
  (correlated, not independent samples). Treat the Cohen's d values as directional, not
  precise.
- **This package is unusually densely connected.** 43/105 (41%) of all possible object
  pairs qualify as "related," largely because a few tables (`ZORDER_HEADER`: 6 objects,
  `ZCUST_MASTER`: 5 objects) are shared very broadly. A real, larger ABAP package may have
  much sparser table sharing, which would change both the size and the composition of the
  "related" group in ways this sample can't predict.
- **The code-aware model was trained on code-search-net languages** (Python, Java,
  JavaScript, PHP, Ruby, Go) — not ABAP. Its weak showing here may reflect that ABAP is
  simply out-of-distribution for it, not that code-aware models in general can't help;
  a different code model or one fine-tuned/prompted with ABAP-aware conventions might do
  better. This investigation only rules out *this specific* model on *this specific* file.
- **The `ENDCLASS.` chunking artifact** (see above) affects results more at small scale
  than it would on a larger, more varied package, though filtering it out didn't change the
  overlap conclusion here.
- These results are specific to `ZORDER_MGMT_extract.txt`. Re-run `embedding_bench.py`
  against a larger real extraction once one exists — that's exactly what it was built for.

## Deliverables produced

1. [`lld_step2/embedding_bench.py`](../lld_step2/embedding_bench.py) — reusable benchmark:
   takes `embedding_source` as a parameter (`"original"` or any model name already stored
   via `alt_embedding.py`), derives labeled pairs mechanically from the graph, and reports
   mean/median/stdev, overlap fraction, and a text histogram. Also runnable as a CLI.
2. [`lld_step2/alt_embedding.py`](../lld_step2/alt_embedding.py) — computes and stores a
   second model's embeddings in a new, investigation-only `investigation_chunk_embeddings`
   table (created by this script, not part of `sql/init.sql`), keyed by
   `(chunk_id, model_name)`, without touching `code_chunks.embedding`.
3. This report.
