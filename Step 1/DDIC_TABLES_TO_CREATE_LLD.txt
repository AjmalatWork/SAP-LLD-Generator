DDIC tables for ZLLD_PACKAGE_EXTRACTOR (LLD tool, step 1)
===========================================================================
STATUS: created in the system, as ZDCCRT_SYNC_LOG / ZDCCRT_SYNC_OBJ (not the
original ZLLD_* names below - PACKAGE was also renamed to ZPACKAGE, and
OBJ_TYPE/OBJ_NAME use TROBJTYPE/TROBJ_NAME data elements instead of E071's
own OBJECT/OBJ_NAME). ZLLD_PACKAGE_EXTRACTOR.txt has been updated to match
these actual names/fields - see the field tables below for what was
actually built.

1) Table ZDCCRT_SYNC_LOG  ("one row per package, its sync state")
   Short text: LLD Extractor - Package Sync Log

   Field            Key   Data Element   Data Type   Length   Notes
   ---------------  ----  -------------  ----------  -------  ----------------------------------
   MANDT            X     MANDT          CLNT        3        client
   ZPACKAGE         X     DEVCLASS       CHAR        30       package (renamed from PACKAGE)
   LAST_SYNC_TS           TIMESTAMPL     DEC         21,7     UTC timestamp of last successful run
   LAST_TRKORR_HWM         TRKORR         CHAR        20       highest released TR considered so far
   RUN_TYPE                CHAR4          CHAR        4        'FULL' or 'INCR' (last run's type)
   OBJECT_COUNT             INT4           INT4        10       objects extracted in the last run
   STATUS                   CHAR10         CHAR        10       'SUCCESS' / 'FAILED' / 'PARTIAL'

   Notes:
   - Only ONE row per package - written/updated by UPDATE_SYNC_LOG after a
     run completes (MODIFY, not INSERT, so a retried run overwrites cleanly).
   - No row for a package = "never synced" = next run is FULL. This is the
     literal signal ZLLD_PACKAGE_EXTRACTOR's MAIN form checks first.
   - STATUS is written but not currently read back by anything in this
     report (kept for manual troubleshooting / a future dashboard) - a
     FAILED run does not currently roll back or retry automatically; see
     LLD_EXTRACTOR_DESIGN_NOTES.md, "Known gaps," for this limitation.

2) Table ZDCCRT_SYNC_OBJ  ("object list from the last successful run,
   for deletion detection")
   Short text: LLD Extractor - Package Object Snapshot

   Field         Key   Data Element  Data Type   Length   Notes
   ------------  ----  ------------  ----------  -------  --------------------------------------
   MANDT         X     MANDT         CLNT        3        client
   ZPACKAGE      X     DEVCLASS      CHAR        30       package (renamed from PACKAGE)
   OBJ_TYPE      X     TROBJTYPE     CHAR        4        primary key part - values used: PROG/CLAS/FUNC only
   OBJ_NAME      X     TROBJ_NAME    CHAR        120      primary key part
   LAST_SEEN_TS        TIMESTAMPL    DEC         21,7     when this row was last (re)written

   Notes:
   - Rows are at FUNCTION-MODULE granularity for function groups (a FUGR
     itself is never stored here - its member FUNCs are, individually),
     matching what ZLLD_PACKAGE_EXTRACTOR actually extracts. This means a
     function module removed from a function group is detected as a
     removed FUNC even if the function group itself still exists.
   - REFRESH_SYNC_OBJECTS (in the report) deletes and re-inserts this
     package's full row set after every successful run (FULL or INCR) -
     it is a full snapshot each time, not an append-only log.

3) Table ZLLD_STG_RUN  ("one row per DB-mode extraction run")
   Short text: LLD Extractor - DB-Mode Run Header

   Field            Key   Data Element   Data Type   Length   Notes
   ---------------  ----  -------------  ----------  -------  ----------------------------------
   MANDT            X     MANDT          CLNT        3        client
   RUN_ID           X     SYSUUID_X16    RAW         16       generated at start of DB-mode run (CL_SYSTEM_UUID)
   ZPACKAGE               DEVCLASS       CHAR        30       package (same rename precedent as ZDCCRT_SYNC_LOG)
   RUN_TYPE               CHAR4          CHAR        4        'FULL' or 'INCR' - from existing sync logic, unchanged
   EXTRACTED_AT            TIMESTAMP      DEC         15       UTC timestamp (GET TIME STAMP FIELD)
   REMOVED_OBJECTS          STRING         STRING      -        comma-separated "TYPE:NAME" list, or 'NONE' - same format/logic as the file header's REMOVED_OBJECTS line (BUILD_REMOVED_OBJECTS_LIST)
   STATUS                    CHAR12         CHAR        12       'EXTRACTED' / 'PROCESSING' / 'PROCESSED' / 'FAILED' - report sets 'EXTRACTED'; ZLLD_PROCESS_EXTRACTION_RUN's stub sets 'STUB_OK' (fits within CHAR12)

   Notes:
   - RUN_ID is the join key across all four staging tables.
   - VERIFY: SYSUUID_X16 as a data element name may not exist as a
     reusable DDIC data element on your system the way DEVCLASS/CHAR4 do -
     if SE11 rejects it, define the field directly as RAW 16 instead.

4) Table ZLLD_STG_OBJECT  ("one row per staged object")
   Short text: LLD Extractor - DB-Mode Staged Objects

   Field         Key   Data Element   Data Type   Length   Notes
   ------------  ----  -------------  ----------  -------  --------------------------------------
   MANDT         X     MANDT          CLNT        3        client
   RUN_ID        X     SYSUUID_X16    RAW         16
   OBJECT_NAME   X     SEOCLSNAME     CHAR        30       widen if a real PROG/FUNC name ever exceeds this - SEOCLSNAME is a CLAS-oriented data element reused here for convenience, per the brief
   OBJECT_TYPE         CHAR4          CHAR        4        'CLAS' / 'PROG' / 'FUNC' (E071-OBJECT's short codes, not the LLD_TYPE long name file mode's TYPE: line uses)
   ZPACKAGE            DEVCLASS       CHAR        30
   SOURCE              STRING         STRING      -        full source, newline-joined, exactly as GET_SOURCE_FOR_LLD_OBJECT already returns it

   Notes:
   - Same (RUN_ID, OBJECT_NAME) key as ZLLD_STG_DEPENDENCY - a run never
     extracts the same object name twice (BUILD_UNIQUE_LLD_OBJECTS already
     dedupes upstream), so this is a safe primary key, not just a
     convenience.

5) Table ZLLD_STG_DEPENDENCY  ("one row per dependency entry")
   Short text: LLD Extractor - DB-Mode Staged Dependencies

   Field            Key   Data Element   Data Type   Length   Notes
   ---------------  ----  -------------  ----------  -------  ----------------------------------
   MANDT            X     MANDT          CLNT        3        client
   RUN_ID           X     SYSUUID_X16    RAW         16
   OBJECT_NAME      X     SEOCLSNAME     CHAR        30       the object this dependency belongs to
   DEPENDENCY_SEQ   X     INT4           INT4        10       preserves original array order
   DEPENDENCY_TYPE        STRING         STRING      -        raw type exactly as ZCR_GET_DEPENDENCY_OBJ_NEW emits it - METH/OM/CLAS/TABL/etc, open vocabulary, no CHECK constraint
   DEPENDENCY_NAME        STRING         STRING      -
   SIGNATURE_JSON         STRING         STRING      -        kept as an opaque blob - not touched by step 2/3-equivalent scoring, only read by a later processing step

6) Table ZLLD_STG_DDIC  ("one row per DDIC object referenced by the package")
   Short text: LLD Extractor - DB-Mode Staged DDIC Info

   Field         Key   Data Element   Data Type   Length   Notes
   ------------  ----  -------------  ----------  -------  --------------------------------------
   MANDT         X     MANDT          CLNT        3        client
   RUN_ID        X     SYSUUID_X16    RAW         16
   DDIC_TYPE     X     CHAR4          CHAR        4        DOMA / DTEL / TABL / STRU / TTYP
   DDIC_NAME     X     STRING         STRING      -        VERIFY: STRING cannot be a full table key component in some releases (only the last key field may need special handling, or STRING may need to move out of the key entirely with a separate technical key) - if SE11 rejects STRING in the key, use a CHAR-length data element sized to the longest real DDIC object name instead (e.g. CHAR 30, matching DEVCLASS-scale names elsewhere in this file)
   DETAIL_JSON             STRING         STRING      -        kept as an opaque blob for the same reason as SIGNATURE_JSON above

   Notes:
   - STAGE_PACKAGE_DDIC (in the report) uses MODIFY, not INSERT, so a
     duplicate (RUN_ID, DDIC_TYPE, DDIC_NAME) - not expected from this
     report's own single-package DDIC call, but cheap to guard against -
     overwrites rather than erroring.
