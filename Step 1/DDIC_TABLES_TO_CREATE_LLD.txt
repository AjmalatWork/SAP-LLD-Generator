DDIC tables for ZLLD_PACKAGE_EXTRACTOR (LLD tool, step 1)
===========================================================================
STATUS: created in the system, as ZDCCRT_SYNC_LOG / ZDCCRT_SYNC_OBJ (not the
original ZLLD_* names below - PACKAGE was also renamed to ZPACKAGE, and
OBJ_TYPE/OBJ_NAME use TROBJTYPE/TROBJ_NAME data elements instead of E071's
own OBJECT/OBJ_NAME). ZLLD_PACKAGE_EXTRACTOR.txt has been updated to match
these actual names/fields - see the field tables below for what was
actually built.

1) Table ZDCCRT_SYNC_LOG  ("one row per package, its sync state")
   Short text: LLD Extractor - Package Sync Log

   Field            Key   Data Element   Data Type   Length   Notes
   ---------------  ----  -------------  ----------  -------  ----------------------------------
   MANDT            X     MANDT          CLNT        3        client
   ZPACKAGE         X     DEVCLASS       CHAR        30       package (renamed from PACKAGE)
   LAST_SYNC_TS           TIMESTAMPL     DEC         21,7     UTC timestamp of last successful run
   LAST_TRKORR_HWM         TRKORR         CHAR        20       highest released TR considered so far
   RUN_TYPE                CHAR4          CHAR        4        'FULL' or 'INCR' (last run's type)
   OBJECT_COUNT             INT4           INT4        10       objects extracted in the last run
   STATUS                   CHAR10         CHAR        10       'SUCCESS' / 'FAILED' / 'PARTIAL'

   Notes:
   - Only ONE row per package - written/updated by UPDATE_SYNC_LOG after a
     run completes (MODIFY, not INSERT, so a retried run overwrites cleanly).
   - No row for a package = "never synced" = next run is FULL. This is the
     literal signal ZLLD_PACKAGE_EXTRACTOR's MAIN form checks first.
   - STATUS is written but not currently read back by anything in this
     report (kept for manual troubleshooting / a future dashboard) - a
     FAILED run does not currently roll back or retry automatically; see
     LLD_EXTRACTOR_DESIGN_NOTES.md, "Known gaps," for this limitation.

2) Table ZDCCRT_SYNC_OBJ  ("object list from the last successful run,
   for deletion detection")
   Short text: LLD Extractor - Package Object Snapshot

   Field         Key   Data Element  Data Type   Length   Notes
   ------------  ----  ------------  ----------  -------  --------------------------------------
   MANDT         X     MANDT         CLNT        3        client
   ZPACKAGE      X     DEVCLASS      CHAR        30       package (renamed from PACKAGE)
   OBJ_TYPE      X     TROBJTYPE     CHAR        4        primary key part - values used: PROG/CLAS/FUNC only
   OBJ_NAME      X     TROBJ_NAME    CHAR        120      primary key part
   LAST_SEEN_TS        TIMESTAMPL    DEC         21,7     when this row was last (re)written

   Notes:
   - Rows are at FUNCTION-MODULE granularity for function groups (a FUGR
     itself is never stored here - its member FUNCs are, individually),
     matching what ZLLD_PACKAGE_EXTRACTOR actually extracts. This means a
     function module removed from a function group is detected as a
     removed FUNC even if the function group itself still exists.
   - REFRESH_SYNC_OBJECTS (in the report) deletes and re-inserts this
     package's full row set after every successful run (FULL or INCR) -
     it is a full snapshot each time, not an append-only log.

DB output mode (step1_db_mode_brief.md) - STATUS: created, as-built names below
===========================================================================
Renamed the same way ZDCCRT_SYNC_LOG/OBJ were: ZLLD_ prefix -> ZDCCRT_, plus
per-table shortenings (STG_OBJECT -> STG_OBJ, STG_DEPENDENCY -> STG_DEP) and
OBJECT_NAME -> OBJ_NAME throughout. ZLLD_PACKAGE_EXTRACTOR.txt has been
updated to match - see the field tables below for what was actually built.

~~OUTSTANDING ISSUE~~ - FIXED: ZDCCRT_STG_DEP's key was originally missing
DEPENDENCY_SEQ (only MANDT, RUN_ID, OBJ_NAME), which would have failed every
dependency after the first per object with a duplicate-key error.
DEPENDENCY_SEQ has now been added to the key (MANDT, RUN_ID, OBJ_NAME,
DEPENDENCY_SEQ) - see table 5 below.

3) Table ZDCCRT_STG_RUN  ("one row per DB-mode extraction run")
   Short text: LLD Extractor - DB-Mode Run Header

   Field            Key   Data Element   Data Type   Length   Notes
   ---------------  ----  -------------  ----------  -------  ----------------------------------
   MANDT            X     MANDT          CLNT        3        client
   RUN_ID           X     SYSUUID_X16    RAW         16       generated at start of DB-mode run (CL_SYSTEM_UUID)
   ZPACKAGE               DEVCLASS       CHAR        30       package
   RUN_TYPE               CHAR4          CHAR        4        'FULL' or 'INCR' - from existing sync logic, unchanged
   EXTRACTED_AT            TIMESTAMPL     DEC         21,7     UTC timestamp - built as TIMESTAMPL (long form, same data element ZDCCRT_SYNC_LOG-LAST_SYNC_TS uses), not the plain TIMESTAMP originally proposed; ZLLD_PACKAGE_EXTRACTOR.txt's STAGE_EXTRACTION_RUN was updated to declare its local timestamp variable as TIMESTAMPL to match
   REMOVED_OBJECTS          Z_STRING (STRING)  STRING  -      comma-separated "TYPE:NAME" list, or 'NONE' - same format/logic as the file header's REMOVED_OBJECTS line (BUILD_REMOVED_OBJECTS_LIST); Z_STRING is a locally-created data element wrapping STRING, not a rename of the field itself
   STATUS                    CHAR12         CHAR        12       'EXTRACTED' / 'PROCESSED' / 'FAILED' - report sets 'EXTRACTED'; ZLLD_EXTRACT_TO_DB sets 'PROCESSED' or 'FAILED' (the earlier stub's 'STUB_OK' value no longer applies now that ZLLD_EXTRACT_TO_DB has real logic - see step2_native_processing_brief.md)
   ERROR_MESSAGE            Z_STRING (STRING)  STRING  -      set by ZLLD_EXTRACT_TO_DB on a FAILED run, cleared on PROCESSED - lets a failure be diagnosed without SM21/debugging

   Notes:
   - RUN_ID is the join key across all four staging tables.
   - CONFIRMED built with RAW 16 via the SYSUUID_X16 data element - no
     issue on this system.

   Field         Key   Data Element   Data Type   Length   Notes
   ------------  ----  -------------  ----------  -------  --------------------------------------

Native processing / query-ready tables (step2_native_processing_brief.md)
STATUS: created, as-built names below
===========================================================================
Built for EXTRACT_TO_DB, a FORM folded directly into ZLLD_PACKAGE_EXTRACTOR
via "INCLUDE zlld_extract_to_db_f01." (no separate function module - see
Step 1/Include ZLLD_EXTRACT_TO_DB_F01.txt). These are the tables
ZLLD_RETRIEVE_CANDIDATES queries - none of them are staging tables.

Renamed the same way as the DB-mode tables above: ZLLD_ prefix -> ZDCCRT_,
plus OBJECT_NAME -> OBJ_NAME (ZDCCRT_OBJECTS, ZDCCRT_CHUNKS), OBJECT_TYPE ->
OBJ_TYPE (ZDCCRT_OBJECTS), PACKAGE -> ZPACKAGE (ZDCCRT_OBJECTS,
ZDCCRT_DDIC_OBJ), and NAME -> DDIC_NAME (ZDCCRT_DDIC_OBJ). ZLLD_OBJ_DDIC_REF
-> ZDCCRT_OBJ_DDREF and ZLLD_DDIC_OBJECTS -> ZDCCRT_DDIC_OBJ shortened the
table name itself too. Both ZLLD_PACKAGE_EXTRACTOR.txt's EXTRACT_TO_DB
include and ZLLD_RETRIEVE_CANDIDATES.txt have been updated to the as-built
names/fields below.

7) Table ZDCCRT_OBJECTS ("one row per final, query-ready object")
   Short text: LLD Extractor - Query-Ready Objects

   Field         Key   Data Element   Data Type   Length   Notes
   ------------  ----  -------------  ----------  -------  --------------------------------------
   MANDT         X     MANDT          CLNT        3        client
   OBJ_NAME      X     SEOCLSNAME     CHAR        30       renamed from OBJECT_NAME; same widen-if-needed caveat as ZDCCRT_STG_OBJ
   OBJ_TYPE            CHAR4          CHAR        4        renamed from OBJECT_TYPE; CLAS / PROG / FUNC
   ZPACKAGE            DEVCLASS       CHAR        30       renamed from PACKAGE, for consistency with every other table in this file

8) Table ZDCCRT_OBJ_CALLS ("one row per dependency edge - every
   DEPENDENCY_TYPE, not just call-like ones")
   Short text: LLD Extractor - Object Dependency Edges

   Field            Key   Data Element   Data Type   Length   Notes
   ---------------  ----  -------------  ----------  -------  ----------------------------------
   MANDT            X     MANDT          CLNT        3        client
   SOURCE_OBJECT    X     SEOCLSNAME     CHAR        30       the object the dependency belongs to
   TARGET_OBJECT    X     CHAR60_CP      CHAR        60       no FK - may be external/unresolved, same open-vocabulary approach as the Python schema; CHAR 60 (not 30) because a METH-type dependency name is CLSNAME(30)+METHNAME(up to 30) concatenated with no separator
   DEPENDENCY_TYPE  X     CHAR10         CHAR        10       raw type exactly as staged - open vocabulary; CHAR 10 matches ZDCCRT_EKIND_MAP-DEPENDENCY_TYPE below exactly (real types observed are all <=4 chars, so this also keeps the two tables join-friendly for the retrieval report)
   EDGE_KIND              Z_STRING (STRING)  STRING  -        normalized, via ZDCCRT_EKIND_MAP
   SIGNATURE_JSON          Z_STRING (STRING)  STRING  -        copied through verbatim from ZDCCRT_STG_DEP, never parsed by ZLLD_EXTRACT_TO_DB

   Notes:
   - Key is (SOURCE_OBJECT, TARGET_OBJECT, DEPENDENCY_TYPE) per the
     brief - written via MODIFY, so if the same object legitimately has
     two distinct dependency rows with the same (target, type) but
     different SIGNATURE_JSON (e.g. two overloaded-looking calls), only
     the last one processed survives. This is a known, brief-specified
     behavior (not a bug introduced here) - flagged in
     LLD_EXTRACTOR_DESIGN_NOTES.md as something to watch for if the
     ZZBA91 acceptance-criteria row count (474) doesn't match exactly.

9) Table ZDCCRT_OBJ_DDREF ("structured index of DDIC-type dependencies,
   split out of ZDCCRT_OBJ_CALLS for the future table-sharing bonus")
   Short text: LLD Extractor - Object to DDIC References

   Field             Key   Data Element   Data Type   Length   Notes
   ----------------  ----  -------------  ----------  -------  --------------------------------------
   MANDT             X     MANDT          CLNT        3        client
   OBJ_NAME          X     SEOCLSNAME     CHAR        30       renamed from OBJECT_NAME
   DDIC_TYPE         X     CHAR4          CHAR        4        DOMA / DTEL / TABL / STRU / TTYP
   DDIC_OBJECT_NAME  X     CHAR30         CHAR        30       built with CHAR 30 directly - real DDIC object names are max 30 chars

   Notes:
   - Populated for EVERY DDIC-shaped dependency type, not just TABL -

     scope in this build, but wants this table shaped so a future

     DDIC_TYPE(s) actually count toward that bonus is decided later,
     with real lexical-score evidence, not here.

13) Table ZDCCRT_EKIND_MAP ("maintainable DEPENDENCY_TYPE -> EDGE_KIND

    Short text: LLD Extractor - Edge Kind Mapping

    Field            Key   Data Element   Data Type   Length   Notes
    ---------------  ----  -------------  ----------  -------  ----------------------------------
    MANDT            X     MANDT          CLNT        3        client
    DEPENDENCY_TYPE  X     CHAR10         CHAR        10       raw type (METH/OM/CLAS/TABL/etc.) - matches ZDCCRT_OBJ_CALLS-DEPENDENCY_TYPE's type exactly (see above), which matters since ZLLD_RETRIEVE_CANDIDATES joins the two
